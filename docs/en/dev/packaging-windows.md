# Windows packaging (MSIX)

> [简体中文](../../zh-CN/dev/packaging-windows.md)

The Windows packaging of vfox+ is two commands of `vfxtool`:
`vfxtool build-msix` turns staged Windows executables into unsigned `.msix`
packages (one per architecture) and a `.msixbundle` for **Windows 11**, and
`vfxtool sign-msix` signs them with a certificate of its own and installs the
bundle (see [Signing the packages yourself](#signing-the-packages-yourself)).
`shared/packaging/windows/` holds only a pointer to this page.

The package identity, the manifest, the logos and the bundle layout are
generated by `vfxtool build-msix`
(`shared/tooling/internal/buildmsix`); nothing binary is committed here. The
logos are the application icon, drawn at build time from the paths of its SVG
by `shared/tooling/internal/appicon` (see the
[design system](design-system.md#application-icon)).

## What is built

For each architecture (`x64` for AMD64, `arm64` for ARM64):

- `vfox-plus_<version>_<arch>.msix`: an unsigned OPC ZIP with
  `AppxManifest.xml`, `[Content_Types].xml`, `AppxBlockMap.xml`, the
  executable (for example `vfox-plus.exe`) and the `Assets/` logos.
- `vfox-plus_<version>.msixbundle`: the regular bundle containing the
  `.msix` files with `AppxMetadata/AppxBundleManifest.xml`.

The identity defaults to `dev.vfox.VfoxPlus` (the same as the Linux desktop
entry) and the publisher to `CN=vfox-plus` with the unsigned-package OID
(`OID.2.25.311729368913984317654407730594956997722=1`), which Windows 11
requires for `-AllowUnsigned` installs. The target device family is
`Windows.Desktop` with `MinVersion 10.0.22000.0` (Windows 11).

## Building

Cross-compile on any OS (mygo needs no C compiler), then package:

```sh
vfxtool build --goos windows --goarch amd64 --root mygo stage-x64/vfox-plus.exe
vfxtool build --goos windows --goarch arm64 --root mygo stage-arm64/vfox-plus.exe
SOURCE_DATE_EPOCH="$(git log -1 --format=%ct)" vfxtool build-msix \
  --package vfox-plus --version "$(tr -d '[:space:]' < mygo/VERSION)" \
  --stage-x64 stage-x64 --stage-arm64 stage-arm64 \
  --executable vfox-plus.exe dist
```

Only one `--stage-*` is needed for a single-architecture bundle. The output is
reproducible: ZIP entries are stored (no compression), sorted, with timestamps
from `SOURCE_DATE_EPOCH`.

## Installing on Windows 11

Extract the `vfox-plus-windows` artifact (it holds the unsigned packages next
to the staged executables and a Windows `vfxtool.exe`), then install the
bundle in an elevated PowerShell:

```powershell
Add-AppxPackage -Path .\vfox-plus_0.1.0.msixbundle -AllowUnsigned
```

The deployment platform picks the slice matching the machine, and the package
installs for all users. To remove it again:

```powershell
Remove-AppxPackage -Package dev.vfox.VfoxPlus_<version>_neutral_~_<publisher-id>
```

(Get the full package name with `Get-AppxPackage -Name dev.vfox.VfoxPlus`.)

To run from source without packaging, build on Windows and run the exe
directly.

## Signing status

The `.msix` and `.msixbundle` files are currently **unsigned**. They install
with `Add-AppxPackage -AllowUnsigned` as above, and no self-signing is needed.
An officially signed bundle will be provided later.

## Signing the packages yourself

`vfxtool sign-msix` signs the bundle with a certificate that it makes and installs
it, for a machine where the bundle should install without `-AllowUnsigned`, and
for whoever tests the signed path. It replaces the former `Sign-Msix.ps1`. Run it
from the extracted `vfox-plus-windows` artifact, which holds `stage-x64/`,
`stage-arm64/`, `vfxtool.exe` and the unsigned packages:

```powershell
.\vfxtool.exe sign-msix
```

It does this, in this order:

1. It downloads osslsigncode 2.14 into `tools/`, pinned and checked by its SHA-256,
   so that no Windows SDK is needed. `--osslsigncode PATH` takes one that you
   have instead, and `--force` downloads again.
2. It rebuilds the packages into `signed/` with the publisher `CN=vfox-plus`
   (`--publisher-cn`) instead of the OID of unsigned packages, because the
   publisher of a signed package must equal the subject of the certificate.
3. It makes a self-signed code-signing certificate for that subject (RSA 2048,
   valid for five years) and signs every `.msix`, then the bundle.
4. It trusts the certificate for the local machine, in its `TrustedPeople` store,
   which is what the sideloading of a signed package looks at, and takes out the
   certificate that an earlier run added.
5. It installs the bundle with `Add-AppxPackage` (`--skip-install` stops before).

The private key lives for one run: it goes to a temporary file for osslsigncode
and is deleted after the signing, never kept. The certificate that stays trusted
on the machine can therefore sign nothing any more, and there is no key to
protect. The price is that each run makes a new certificate, so a bundle that an
earlier run signed does not install any more: sign again and install the new one.

Trusting a certificate and installing a package need administrator rights. In a
shell that is not elevated the command asks Windows to start a copy of itself with
them: you answer the UAC prompt, and the copy works in a window of its own, which
waits for Enter at the end so that you can read what it did. In an elevated shell
it simply runs; `--no-relaunch` makes it fail instead of asking, for scripts. Other
systems have no store and no installation, so there the command only signs: pass
`--skip-install` and an `--osslsigncode` of that system.

To take it away again, remove the package (see above) and the certificate:

```powershell
Get-ChildItem Cert:\LocalMachine\TrustedPeople |
  Where-Object Subject -eq "CN=vfox-plus" | Remove-Item
```

The `validate-windows` job of [`mygo.yml`](../../../.github/workflows/mygo.yml) runs
the command on Windows Server 2025 (x64) and Windows 11 on ARM (arm64): it signs,
installs without `-AllowUnsigned`, checks the architecture, uninstalls, runs a
second time and checks that exactly one certificate is trusted. The elevated copy
is the one path that CI cannot take, because its runners are administrators with UAC
off; it needs a run on a machine with UAC after a change.

## Signing notes (for maintainers)

- A signed package's publisher must exactly equal the certificate subject, with
  no OID — which is why signing rebuilds the packages instead of signing the
  unsigned ones in place (their publisher carries the unsigned-package OID).
- For public distribution without any per-machine step, either publish to the
  Microsoft Store (Microsoft signs) or sign with a publicly trusted
  code-signing certificate or Azure Trusted Signing; the build is the same,
  only `--publisher` and the signing step change.
